# Robust mode: ส่งผ่าน LINE หรือ Telegram แบบรูปภาพได้

โหมดปกติของ SweetHide ซ่อนข้อมูลในบิตต่ำสุดของพิกเซล ซึ่งเก็บได้เยอะและมองไม่เห็นเลย แต่ถ้ารูปถูกบีบอัดใหม่แม้แต่นิดเดียว ข้อมูลก็หายหมด เลยต้องส่งเป็น **ไฟล์** เสมอ

Robust mode คือทางเลือกสำหรับตอนที่อยากกดส่งเป็น **รูป** ธรรมดาในแชต แลกกับการเก็บข้อมูลได้น้อยลงมาก (ประมาณ 100–450 ไบต์ต่อรูป พอสำหรับข้อความสั้น ๆ หรือลิงก์ แต่แนบไฟล์ไม่ได้) และรูปที่ส่งจะถูกย่อลงเหลือราว 1.3 ล้านพิกเซล

> สถานะ: ส่วนประมวลผลสัญญาณ (ฝัง/ถอด, error correction, profile) อยู่ใน `SweetHide.Core.Robust` แล้ว ส่วนการเข้ารหัสด้วยรหัสผ่าน, CLI และแอปกำลังต่อเข้ามา

## ใช้กับแอปไหนได้บ้าง

| แอป | วิธีส่ง | ต้องใช้ robust mode ไหม |
|---|---|---|
| LINE | ส่งรูปปกติ (ไม่ได้ติ๊ก "ต้นฉบับ/Original" และไม่ได้ส่งเป็นไฟล์) | ใช้ profile `line` |
| Telegram | ส่งเป็นรูป (ไม่ใช่ "ส่งแบบไฟล์") | ใช้ profile `telegram` |
| Discord | แนบไฟล์ตามปกติ | **ไม่ต้อง** ส่ง PNG จากโหมดปกติได้เลย ดูหมายเหตุด้านล่าง |
| Facebook / Messenger | | **ไม่รองรับ** และไม่มีแผนจะทำ เพราะ Meta ย่อรูปได้หลายขนาด อาจแปลงเป็น WebP และเปลี่ยนวิธีบีบอัดได้ทุกเมื่อ ถ้าจะส่งทางนี้ให้ส่งเป็นไฟล์ (zip) แล้วใช้โหมดปกติ |

ถ้าเลือกได้ การส่งเป็นไฟล์ (หรือติ๊ก "ต้นฉบับ" ใน LINE) ยังดีที่สุดเสมอ เพราะใช้โหมดปกติได้ เก็บได้เป็นเมกะไบต์ และไม่มีอะไรเสียหาย

**Discord:** ไฟล์แนบที่ส่งจากคอมพิวเตอร์หรือเว็บถูกเก็บไว้ตามที่อัปโหลด ส่วนที่เห็นในแชตเป็นแค่ภาพตัวอย่างที่ย่อแล้ว ให้ผู้รับกด "เปิดต้นฉบับ" หรือดาวน์โหลดไฟล์ แล้วค่อยถอด มีข้อควรระวังสองข้อ คือบนมือถือถ้าเปิด Data Saving Mode แล้วใช้เน็ตมือถือ รูปจะถูกอัปโหลดแค่ 360p และไฟล์ที่ใหญ่เกินลิมิต (บัญชีฟรี 10 MB) จะมีปุ่ม "Send Compressed" ซึ่งห้ามกด เรายังไม่ได้ทดสอบกับบัญชีจริงว่าไฟล์ PNG ที่ได้คืนมาตรงกันทุกไบต์ ถ้าจะให้ชัวร์ ลองเทียบ `sha256sum` ของไฟล์ก่อนส่งและหลังดาวน์โหลดดูก่อน

## ความจุ

รูปจะถูกย่อให้เล็กกว่าขนาดที่แอปจะย่อเองเสมอ (ถ้ารูปเล็กกว่านั้นอยู่แล้วจะไม่ขยาย) ความจุจึงขึ้นกับสัดส่วนของรูปมากกว่าความละเอียดของกล้อง

| รูปต้นฉบับ | LINE: ขนาดที่ส่ง → ความจุ | Telegram: ขนาดที่ส่ง → ความจุ |
|---|---|---|
| 4:3 เช่น 4000×3000 (12 MP) | 1385×1039 → 321 ไบต์ | 1280×960 → 342 ไบต์ |
| 3:4 แนวตั้ง | 1039×1385 → 321 ไบต์ | 960×1280 → 342 ไบต์ |
| 3:2 เช่น 6000×4000 | 1440×960 → 310 ไบต์ | 1280×853 → 298 ไบต์ |
| 16:9 เช่น 1920×1080 | 1440×810 → 257 ไบต์ | 1280×720 → 248 ไบต์ |
| 1:1 เช่น 3000×3000 | 1200×1200 → 324 ไบต์ | 1280×1280 → 466 ไบต์ |
| 800×600 (ไม่ถูกย่อ) | 90 ไบต์ | 114 ไบต์ |

ตัวเลขนี้คือพื้นที่ดิบ พอเข้ารหัสด้วยรหัสผ่านแล้วจะเหลือให้ข้อความน้อยลงอีกหน่อย (ส่วนหัวของการเข้ารหัส) ตัวอักษรไทยใช้ 3 ไบต์ใน UTF-8 แม้จะถูกบีบอัดก่อนก็ตาม รูป 12 MP จึงใส่ข้อความอังกฤษได้ราว 250 ตัวอักษร หรือภาษาไทยราว 80–150 ตัวอักษร ขึ้นกับว่าบีบอัดได้แค่ไหน

## อะไรรอด อะไรไม่รอด

ผลข้างล่างวัดจากรูปสังเคราะห์ขนาด 12 MP ที่มีทั้งท้องฟ้าเรียบ พื้นผิวหยาบ ขอบคม ส่วนที่ขาวจนสุดและมืดจนสุด ใส่ข้อมูลเต็มความจุ แล้วจำลองแอปด้วย libjpeg-turbo (ผ่าน SkiaSharp) ซึ่งเป็นตัวเข้ารหัส JPEG ตัวเดียวกับที่ Android และแอปส่วนใหญ่ใช้ ขั้นตอนคือ ฝัง → บันทึกเป็น JPEG ตามคุณภาพของ profile (สิ่งที่เราส่งจริง) → แอปบีบอัดใหม่ → ถอด

| สิ่งที่เกิดกับรูประหว่างทาง | LINE | Telegram |
|---|---|---|
| บีบอัด JPEG ใหม่ที่คุณภาพ 50–95 (chroma 4:2:0 หรือ 4:4:4) | ✅ รอด | ✅ รอด |
| คุณภาพ 40 (บิตเพี้ยนดิบ ~6–9%) | ✅ รอด | ✅ รอด |
| คุณภาพ 35 | ✅ รอด | ✅ รอด |
| คุณภาพ 30 | ⚠️ เจอแต่เสียหาย | ⚠️ เจอแต่เสียหาย |
| คุณภาพ 25 หรือต่ำกว่า | ❌ ไม่พบ | ❌ ไม่พบ |
| บีบอัดซ้ำสองรอบ (80 แล้ว 65–70) | ✅ รอด | ✅ รอด |
| ถูกย่อเพิ่ม 0.95×, 0.8×, 0.75× แล้วบีบอัดที่ 80 | ✅ รอด (กู้ได้แบบ best effort) | ✅ รอด |
| ถูกย่อเพิ่ม 0.9× แล้วบีบอัดที่ 80 | ✅ รอด แต่เฉียดฉิว (บิตเพี้ยน ~19%) | ✅ รอด |
| ถูกย่อเหลือครึ่งเดียว (0.5×) | ❌ ไม่พบ | ❌ ไม่พบ |
| แปลงเป็น WebP (lossy) คุณภาพ 90 | ✅ รอด | ✅ รอด |
| แปลงเป็น WebP (lossy) คุณภาพ 75–80 | ⚠️ เจอแต่เสียหาย | ⚠️ เจอแต่เสียหาย |
| แปลงเป็น WebP คุณภาพ 70 หรือต่ำกว่า | ❌ ไม่พบ | ❌ ไม่พบหรือเสียหาย |
| ครอป, หมุน, ใส่ฟิลเตอร์/สติกเกอร์, แคปหน้าจอ | ❌ ไม่รอด (โดยการออกแบบ ไม่ได้วัดเป็นตัวเลข) | ❌ |
| ใช้รหัสผ่านผิด หรือรูปที่ไม่มีอะไรซ่อน | บอกว่า "ไม่พบ" ไม่ใช่ "เสียหาย" | |

เทสต์อัตโนมัติใน `tests/SweetHide.Core.Tests/Robust/` ตรวจช่วงคุณภาพ 50–90 ทุกครั้งที่ build ส่วนช่วง 35–45 และ 95 มาจากการวัดด้วยมือ ซึ่งยังทำงานได้แต่ไม่ได้ล็อกไว้ในเทสต์

ทุกอย่างข้างบนเป็นการ **จำลอง** ยังไม่ได้ทดสอบกับแอปจริง ตัวเข้ารหัสของ iPhone (Apple ImageIO) และของ LINE อาจใช้ตาราง quantization ต่างจาก libjpeg ก่อนใช้จริงให้ลองส่งหาตัวเองสักรูปก่อน

## รูปจะดูเปลี่ยนไปแค่ไหน

- ตัวการฝังเองทำให้ PSNR อยู่ราว **46 dB** เทียบกับรูปที่ย่อแล้ว ซึ่งปกติมองไม่ออก ถ้าซูม 100% ดูท้องฟ้าหรือผนังเรียบ ๆ อาจเห็นลายจาง ๆ ระดับเดียวกับลาย JPEG ทั่วไป
- ไฟล์ JPEG ที่ส่งออกไป (คุณภาพ 90–92) ได้ PSNR ราว **39.8 dB** เทียบกับรูปที่ย่อแล้ว ถ้าบันทึก JPEG คุณภาพเดียวกันโดยไม่ฝังอะไรจะได้ราว 40.9 dB การฝังจึงเพิ่มความเสียหายแค่ราว 1 dB
- สิ่งที่ผู้รับสังเกตได้ชัดกว่าคือรูปถูกย่อเหลือราว 1.3 MP แต่ก็เป็นขนาดที่แอปจะย่อให้อยู่แล้ว

## ความเร็ว

รูป 12 MP ใช้เวลาฝังราว 0.3–0.4 วินาที (รวมการย่อรูป) และถอดราว 10–30 มิลลิวินาที บนเครื่อง 4 คอร์ ถ้ารูปไม่มีอะไรซ่อนไว้ ตัวถอดต้องลองทุก profile และอาจลองขยายรูปกลับหลายขนาด ซึ่งช้าสุดที่วัดได้คือราว 0.8 วินาที (รูปกล้องขนาดเต็มจะไม่ถูกลองขยาย จึงจบในไม่ถึง 0.1 วินาที)

## ข้อจำกัดและเรื่องความปลอดภัย

- **ซ่อนได้เนียนน้อยกว่าโหมดปกติ** การฝังแบบ QIM ใน DCT ทิ้งรูปแบบทางสถิติที่ steganalysis สมัยใหม่จับได้ง่ายกว่า LSB matching มาก ใช้เพื่อ "ส่งผ่านแอปให้รอด" ไม่ใช่เพื่อ "ไม่ให้ใครสงสัยว่ามีอะไรซ่อนอยู่"
- ตัว robust mode เองไม่ได้เข้ารหัสอะไร ความลับของข้อความมาจากชั้นเข้ารหัส (AES-GCM + Argon2) ที่ครอบอยู่ข้างนอก และตำแหน่งที่ฝังกับลำดับบิตทั้งหมดสุ่มจากกุญแจ 32 ไบต์ที่ได้จากรหัสผ่าน
- **ไม่ทน WebP** WebP ใช้ transform 4×4 และมี filter ลบรอยบล็อก ซึ่งรบกวนสัมประสิทธิ์ 8×8 ที่เราใช้ ตอนนี้ยังไม่มีหลักฐานว่า LINE หรือ Telegram แปลงรูปเป็น WebP แต่ถ้าวันไหนเปลี่ยน profile ปัจจุบันจะใช้ไม่ได้ (การทดลองใน [ROBUST-FACEBOOK-PROPOSAL.md](ROBUST-FACEBOOK-PROPOSAL.md) แสดงว่า step ที่ใหญ่ขึ้นแก้ได้ แลกกับความเนียน)
- ถ้าแอปเปลี่ยนวิธีย่อหรือบีบอัดรูปเมื่อไร ผลข้างบนอาจใช้ไม่ได้อีกต่อไป ค่าใน profile ถูกล็อกไว้ เพราะถ้าเปลี่ยน รูปเก่าจะถอดไม่ออก ถ้าต้องปรับให้ทำเป็น profile ใหม่
- กู้รูปที่ถูกย่อได้เฉพาะกรณีที่รูปต้นฉบับใหญ่กว่าขนาดของ profile (เพราะตัวถอดต้องเดาขนาดเดิมได้) และใช้ได้แค่ช่วง 0.6–1×

## ทำงานยังไง (ฉบับย่อ)

1. **ย่อรูป** ให้เล็กกว่าที่แอปจะย่อเอง แอปจะได้ไม่ย่อซ้ำ และตาราง 8×8 ของ JPEG ที่แอปใช้จะตรงกับของเรา
2. **ฝังบิต** ลงในค่าความสว่าง (Y) ของแต่ละบล็อก 8×8 โดยเลือกสัมประสิทธิ์ DCT ความถี่ต่ำถึงกลาง 1 ตัวต่อบล็อก จาก 7 ตำแหน่ง (zigzag 3–9) ตามกุญแจ แล้วขยับค่าไปอยู่บนตาราง QIM ระยะห่าง 34 ที่เลื่อนด้วยค่า dither ประจำตำแหน่ง พอแอปบีบอัดใหม่ ค่าจะขยับไม่เกินครึ่งหนึ่งของ step ที่แอปใช้ ถ้ายังน้อยกว่า 34/4 บิตก็อ่านกลับได้ตรง
3. **ป้องกันความผิดพลาด** มี sync pattern 64 บิต, header ที่ป้องกันด้วย Reed–Solomon (เวอร์ชันและความยาว), แล้วตามด้วยข้อมูล + CRC-32 ที่แบ่งเป็น codeword ของ Reed–Solomon (parity 60%) ทุกบิตถูกทำซ้ำหลายครั้ง (LINE อย่างน้อย 5 ครั้ง, Telegram 4 ครั้ง) และกระจายไปทั่วรูปด้วย permutation จากกุญแจ
4. **ตอนถอด** รวมค่า soft decision ของทุกสำเนา ถ้าแก้ไม่ได้ จะลองให้ Reed–Solomon ถือไบต์ที่ไม่แน่ใจที่สุดเป็น erasure แล้วถอดใหม่ ค่าความสัมพันธ์กับ sync pattern ใช้แยก "ไม่มีอะไรในรูปนี้" (ใกล้ 0) ออกจาก "มีแต่เสียหาย"

| ค่าใน profile | `line` | `telegram` |
|---|---|---|
| ด้านยาวสุด / จำนวนพิกเซลสูงสุด | 1440 px / 1.44 MP | 1280 px / 1.64 MP |
| QIM step / สัมประสิทธิ์ต่อบล็อก | 34 / 1 | 34 / 1 |
| ทำซ้ำ sync+header / ข้อมูล (ขั้นต่ำ) | 9 / 5 | 9 / 4 |
| Reed–Solomon parity | 60% | 60% |
| คุณภาพ JPEG ที่ส่งออก | 92 | 90 |

## ข้อมูลจากการค้นคว้า (ตรวจเมื่อ 2 พฤศจิกายน 2026)

ข้อมูลข้างล่างไม่ใช่สเปกทางการ แอปเปลี่ยนได้ทุกเมื่อ profile จึงเผื่อระยะไว้ทั้งขนาดและคุณภาพ

### LINE (ส่งรูปปกติ)

- มีตั้งค่า "คุณภาพรูปภาพที่ส่ง" แบบมาตรฐาน/สูง และมีปุ่ม "ต้นฉบับ (Original)" ตอนส่งแต่ละครั้ง ([notebookspec](https://notebookspec.com/web/513526-send-photos-with-line-in-original-size), [kocpc](https://en.kocpc.com.tw/?p=8833))
- ผลวัดของ appllio: รูป 3024×4032 (2.54 MB) ส่งแบบมาตรฐานได้ 1108×1478 (283 KB), แบบคุณภาพสูงได้ 1774×2364 (744 KB), แบบต้นฉบับได้ 3024×4032 (1.9 MB) ([appllio](https://appllio.com/line-send-original-size-photos), ไม่ระบุวันที่ทดสอบ) อีกบล็อกวัดได้ 1108×1477 เหมือนกัน
- **ข้อสันนิษฐานของเรา:** 1108×1478 ≈ 1.64 MP ≈ 1280² และ 1774×2364 ≈ 4.19 MP ≈ 2048² เป๊ะ จึงน่าจะจำกัดที่ **จำนวนพิกเซล** ไม่ใช่ด้านยาว แต่เว็บเครื่องมือแห่งหนึ่งบอกว่าด้านยาวราว 1620 px (มาตรฐาน) และ 2880 px (สูง) ([mamepress](https://mamepress.jp/compress-image-line)) ซึ่งขัดกัน profile `line` จึงย่อให้เล็กกว่าทั้งสองแบบ (≤ 1440 px และ ≤ 1.44 MP)
- LINE ไม่เปิดเผยคุณภาพ JPEG 283 KB สำหรับ 1.64 MP คือราว 1.4 บิตต่อพิกเซล น่าจะอยู่ราวคุณภาพ 75–85 แบบ 4:2:0 (ประมาณเอง) จึงตั้งเป้าให้รอดตั้งแต่คุณภาพ 50 ขึ้นไป
- ไม่ได้ตรวจว่า LINE ลบ metadata หรือไม่ (เราไม่ได้ใส่ metadata อยู่แล้ว)

### Telegram (ส่งเป็นรูป)

อ่านจากซอร์สโค้ดของแอปทางการ (branch หลัก ณ วันที่ตรวจ)

- **Android** ([DrKLO/Telegram](https://github.com/DrKLO/Telegram)): `AndroidUtilities.getPhotoSize()` คืน 1280 (โหมด HD 2560) และ `SendMessagesHelper.generatePhotoSizes()` เข้ารหัสใหม่เป็น JPEG คุณภาพ **80** (HD ใช้ 99) ผ่าน `Bitmap.compress` ของ Android
- **Desktop** ([telegramdesktop/tdesktop](https://github.com/telegramdesktop/tdesktop), `storage/localimageloader.cpp`): จำกัดด้านยาว 1280 (หรือ 2560 ถ้าเปิด "Send large photos") แล้วเข้ารหัสใหม่ที่คุณภาพ **87** แต่ถ้าไฟล์ต้นทางเป็น JPEG ที่ไม่เกินขนาดและไม่เกิน 4 บิตต่อพิกเซล จะเก็บสัมประสิทธิ์เดิมไว้และแค่แปลงเป็น progressive แบบ lossless (`MakeProgressiveJpeg` ใน [lib_ui](https://github.com/desktop-app/lib_ui)) ไฟล์ที่เราส่งออก (1280×960 ราว 200 KB, เพดานคือ 614 KB) จึงน่าจะผ่านไปโดยไม่ถูกแตะเลย
- **iOS** ([TelegramMessenger/Telegram-iOS](https://github.com/TelegramMessenger/Telegram-iOS), `LegacyMediaPickers.swift`): ย่อให้พอดี 1280×1280 (HD 2560×2560) และใช้ `compressImageToJPEG(quality: 0.6)` ซึ่งเป็นสเกลของ Apple ไม่ใช่สเกลเดียวกับ libjpeg ส่วนรูปที่เลือกจากคลังภาพไปผ่านโค้ดอีกชุดที่เราหาไม่เจอ
- มิถุนายน 2025 แอปมือถือเพิ่มปุ่มสลับ SD/HD ตอนส่งรูป ผู้ทดสอบบน iPhone ได้ 960×1280 กับ 1920×2560 ([Droid Life, 3 มิ.ย. 2025](https://www.droid-life.com/2025/06/03/telegram-finally-adds-hd-photo-sharing-toggle/))
- มีกระทู้ใน bugs.telegram.org บอกว่าเซิร์ฟเวอร์บีบอัดรูปซ้ำอีกรอบ แต่เราเปิดเว็บนั้นจากเครื่องที่ใช้ทดสอบไม่ได้ จึงยังยืนยันไม่ได้ (เทสต์บีบอัดซ้ำสองรอบผ่านอยู่แล้ว)

### Discord (ไฟล์แนบ)

- ศูนย์ช่วยเหลือของ Discord: บนมือถือ ถ้าเปิด Data Saving Mode (User Settings → App Settings → Data Consumption) แล้วใช้เน็ตมือถือ รูปจะถูกอัปโหลดที่ 360p ([Discord Help Center](https://support.discord.com/hc/en-us/articles/9665451164951))
- ไฟล์ที่ใหญ่เกินลิมิตจะมีตัวเลือก "Send Compressed" (กระทู้ผู้ใช้ใน [Discord Support Community](https://support.discord.com/hc/de/community/posts/1500000723081-Discord-auto-compresses-images-but-not-video-even-when-clicked-on-Send-Compressed))
- วิทยานิพนธ์ปี 2025 ของ University of Colorado Denver ("Forensic Analysis of Discord JPEG and PNG Processing") รายงานว่า Discord ลบ EXIF ของ JPEG ทั้งหมดและบางครั้งจัดโครงสร้างไฟล์ใหม่ ([PDF](https://artsandmedia.ucdenver.edu/docs/librariesprovider27/alma-mater/nash_thesis_fall2025.pdf)) เราอ่านได้แค่บทคัดย่อ จึงไม่รู้ว่าพิกเซลของ PNG ถูกแตะหรือไม่
- สรุป: กรณีปกติ Discord ไม่ได้บีบอัดไฟล์แนบใหม่ จึงไม่ได้ทำ profile ให้ แต่ยังไม่ได้ยืนยันด้วยบัญชีจริง
