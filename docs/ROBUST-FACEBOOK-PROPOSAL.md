# ข้อเสนอ: robust mode สำหรับ Facebook และ Messenger

> เอกสารนี้เป็นข้อเสนอให้เจ้าของโปรเจกต์ดูก่อนตัดสินใจ **ยังไม่มีโค้ดส่วนนี้** ตัวเลขที่บอกว่า "วัดได้" มาจากการจำลองในเครื่อง (libjpeg-turbo และ libwebp ผ่าน SkiaSharp) ไม่ใช่จาก Facebook จริง ข้อมูลเรื่องแอปตรวจเมื่อ 2 พฤศจิกายน 2026

## สรุปสั้น ๆ

- **ทำได้ แต่แพงกว่า LINE/Telegram ชัดเจน** ถ้าผู้รับได้รูปขนาด 2048 px จะเก็บได้ราว 290 ไบต์ ถ้าได้แค่ 960 px เหลือราว 50 ไบต์ และรูปจะดูเปลี่ยนไปมากขึ้น (PSNR ของการฝังราว 41 dB เทียบกับ 46 dB ใน profile ปัจจุบัน)
- ความเสี่ยงหลักไม่ใช่เรื่องเทคนิค แต่คือ **เราไม่รู้แน่ว่า Facebook ทำอะไรกับรูป** และ Meta เปลี่ยนได้ทุกเมื่อโดยไม่บอก
- **แนะนำ:** ทำแผนทดสอบ Phase A (ข้างล่าง) ก่อน ใช้เวลาราวครึ่งวันและไม่ต้องเขียนโค้ด แค่ส่งรูปที่เตรียมไว้แล้วจดผล พอรู้ว่ารูปถูกย่อเหลือเท่าไร เป็น JPEG หรือ WebP และคุณภาพประมาณไหน ค่อยตัดสินใจว่าจะทำ profile ไหน

## Facebook และ Messenger ทำอะไรกับรูป

### Facebook (โพสต์และอัลบั้ม)

- **ย่อขนาด** คู่มือของบุคคลที่สามหลายแห่งตรงกันว่า Facebook เก็บรูปที่ด้านยาว 2048, 960 หรือ 720 px และรูปขนาดอื่นจะถูกย่อลงมา ([Have Camera Will Travel](https://havecamerawilltravel.com/workflow/images-photos-facebook-sizes-dimensions-types/), [Photography Life](https://photographylife.com/how-to-properly-resize-images-for-facebook)) ไม่มีเอกสารทางการยืนยัน
- **บีบอัดใหม่ทุกรูปและคุณภาพไม่คงที่** งานวิจัยที่อ้างการทดลองก่อนหน้าบอกว่า ถ้ารูปไม่เกิน 512×512 และคุณภาพเดิมไม่เกิน 85 Facebook จะบีบที่ QF 71 ส่วนรูปที่ใหญ่กว่านั้นคุณภาพจะเปลี่ยนไปตามแต่ละรูป ([arXiv 2304.13297](https://arxiv.org/abs/2304.13297), 2023) งานอื่นใช้ QF 75 เป็นตัวแทนของ Facebook ([ScienceDirect, 2026](https://www.sciencedirect.com/science/article/abs/pii/S1047320326001124)) และงานรุ่นเก่าของ Oxford ก็ใช้ 75 เช่นกัน ([Campbell-Moore, 2013](https://www.cs.ox.ac.uk/people/andrew.ker/docs/campbell-moore-secretbook.pdf))
- **ไฟล์ที่ผู้รับได้อาจไม่ใช่ไฟล์ที่เก็บไว้** URL ของรูปบน CDN (`scontent…fbcdn.net`) มี parameter อย่าง `stp=dst-jpg_s960x960` ซึ่งดูเหมือนบอกทั้งรูปแบบไฟล์และขนาด ([ตัวอย่าง URL จริง](https://apify.com/scrapers-hub/facebook-thumbnail-downloader.md)) แปลว่ารูปเดียวกันอาจถูกส่งออกไปหลายขนาดหรือหลายรูปแบบ (อาจรวมถึง WebP) ตามแต่ละหน้าและแต่ละ client ข้อนี้ยังไม่ได้ยืนยัน
- **ครอปและ thumbnail** โพสต์หลายรูปแสดงเป็นภาพครอปใน feed ถ้าผู้รับบันทึกจากตรงนั้น จะได้รูปที่ถูกครอปและย่อ

### Messenger

- **พฤศจิกายน 2017** เริ่มรองรับรูป 4K (4096×4096) ([Meta Newsroom, 2017](https://about.fb.com/news/2017/11/making-visual-messaging-even-better-introducing-high-resolution-photos-in-messenger/)) และมีรายงานว่าก่อนปี 2024 รูปถูกบีบมากหรือน้อยขึ้นกับสภาพเน็ตของทั้งผู้ส่งและผู้รับ ([Android Authority, เม.ย. 2024](https://www.androidauthority.com/messenger-4k-photos-file-limits-3433280))
- **ธันวาคม 2023** แชตส่วนตัวเข้ารหัสแบบ end-to-end เป็นค่าเริ่มต้น ([Meta Newsroom, ธ.ค. 2023](https://about.fb.com/news/2023/12/default-end-to-end-encryption-on-messenger/), [MacRumors, 7 ธ.ค. 2023](https://www.macrumors.com/2023/12/07/facebook-messenger-end-to-end-encryption/)) ข้อสันนิษฐานของเราคือเซิร์ฟเวอร์จึงแตะรูปในแชตส่วนตัวไม่ได้แล้ว การย่อและบีบอัดต้องเกิดในแอปฝั่งผู้ส่ง ซึ่งอาจต่างกันระหว่าง iOS, Android และเว็บ ส่วนแชตกลุ่มในช่วงแรกยังไม่ได้เข้ารหัสแบบนี้ จึงอาจผ่านอีกเส้นทางหนึ่ง
- **เมษายน 2024** เพิ่มปุ่ม HD ตอนส่งรูป Meta บอก The Verge ว่า HD คือ 4096×4096 และถ้าไม่เปิดจะเป็น 2K ([Android Authority](https://www.androidauthority.com/messenger-4k-photos-file-limits-3433280), [Business Today, 11 เม.ย. 2024](https://www.businesstoday.in/technology/news/story/meta-updating-hd-photo-sharing-in-facebook-messenger-and-many-more-features-425102-2024-04-11)) แต่มีรายงานว่าแม้เปิด HD รูปก็ยังถูกบีบอยู่ดี แค่น้อยลง

## ทำไมยากกว่า LINE และ Telegram

1. **บีบหนักกว่าและไม่รู้ตาราง** คุณภาพน่าจะอยู่ราว 70–85 และอาจต่ำกว่านั้น เปลี่ยนไปตามรูป (และตามเน็ตใน Messenger) ตาราง quantization ก็อาจไม่ใช่ของ libjpeg ในขณะที่ Telegram เราเปิดดูโค้ดได้เลยว่าใช้ 80 หรือ 87
2. **มีหลายขนาด** ถ้าเราฝังที่ 2048 px แต่ผู้รับได้ไฟล์ 960 px นั่นคือย่อ 0.47 เท่า ซึ่งเราวัดแล้วว่าข้อมูลหายหมด ไม่ว่าจะตั้งค่าแรงแค่ไหน
3. **อาจเป็น WebP** เราวัดแล้วว่า WebP แบบ lossy ทำลาย profile ปัจจุบัน (step 34) ตั้งแต่คุณภาพ 80 ลงไป เพราะ WebP แปลงทีละบล็อก 4×4 และมี filter ลบรอยบล็อก ซึ่งไปกวนสัมประสิทธิ์ 8×8 ที่เราใช้
4. **ครอป** ทำให้ตาราง 8×8 เลื่อน ถ้าเลื่อนไปแม้พิกเซลเดียว ตัวถอดตอนนี้จะหาไม่เจอ
5. **ยืนยันจากภายนอกไม่ได้** ทุกอย่างข้างบนเป็นข้อสังเกตของคนอื่น และ Meta ปรับระบบได้ทุกเมื่อ

## แนวทางที่เสนอ

### 1. Profile แยกตามขนาดที่ผู้รับได้

แทนที่จะพยายามรอดทุกขนาด ให้ย่อปกให้เท่ากับ tier ที่ต้องการพอดี Facebook จะได้ไม่ย่อซ้ำ

- `facebook-2048` ด้านยาว 2048 px สำหรับ Messenger แบบปกติ/HD และกรณีที่ผู้รับเปิดรูปเต็มแล้วบันทึก
- `facebook-960` ด้านยาว 960 px สำหรับกรณีที่ผู้รับได้แค่รูปขนาดกลาง ความจุน้อยมากแต่รอดในกรณีที่แย่กว่า

ผล Phase A จะบอกว่าควรมีตัวไหนบ้าง

### 2. QIM ที่แรงขึ้นและทำซ้ำมากขึ้น

ใช้กลไกเดิมทั้งหมด (`RobustStego`) แค่เปลี่ยนค่าใน profile: step 64 (เดิม 34), ทำซ้ำอย่างน้อย 10 ครั้ง (เดิม 4–5) และ Reed–Solomon parity 100% (เดิม 60%) ผลการจำลองอยู่ในตารางข้างล่าง ข้อดีคือแทบไม่ต้องเขียนโค้ดใหม่

### 3. Sync template สำหรับกู้ขนาดและตำแหน่ง

- **ขั้นแรก (ถูก ทำได้เลย):** ใช้ขนาดมาตรฐานที่รู้อยู่แล้ว (2048/960/720) เป็นตัวเลือกตอนย่อกลับ แบบเดียวกับที่ robust mode ทำอยู่ตอนนี้ และเพิ่มการหา offset ของตาราง 8×8 (ลองครบ 64 แบบ แล้วดูว่าแบบไหน sync correlation สูงสุด) เพื่อรองรับการครอปไม่กี่พิกเซล ค่า sync ที่มีอยู่แล้วใช้วัดได้เลย ไม่ต้องฝังอะไรเพิ่ม
- **ขั้นที่สอง (ถ้า Phase A พบว่าโดนครอปหรือย่อแบบเดาขนาดไม่ได้):** ฝัง template ในโดเมนความถี่ เช่นจุดยอดใน DFT magnitude ที่ตำแหน่งสุ่มจากกุญแจ หรือ pattern ที่ซ้ำเป็นคาบให้หาด้วย autocorrelation ใช้ประมาณ scale และการเลื่อนก่อนถอด เป็นเทคนิคมาตรฐานของงาน watermarking แต่รูปจะเสียคุณภาพเพิ่มอีกและใช้เวลาทำ 2–4 วัน

### 4. สิ่งที่ไม่แนะนำ

**Transport Channel Matching** (อัปโหลดรูปเดิมซ้ำหลายรอบจน Facebook ไม่เปลี่ยนมันอีก แล้วค่อยฝัง) ได้ผลดีในงานวิจัย แต่ต้องอัปโหลดซ้ำหลายครั้งต่อรูป ซึ่งช้า ทิ้งร่องรอย และถ้าทำแบบอัตโนมัติจะขัดกับเงื่อนไขการใช้งาน

## ความจุและความทนทานที่คาด (จากการจำลอง)

รูปสังเคราะห์ 12 MP ชุดเดียวกับใน [ROBUST.md](ROBUST.md) ฝังเต็มความจุ บันทึกเป็น JPEG คุณภาพ 92 แล้วจำลองการบีบอัดของแพลตฟอร์ม ค่าในวงเล็บคือบิตเพี้ยนดิบก่อนแก้

| | `facebook-2048` (ตัวอย่าง) | `facebook-960` (ตัวอย่าง) | `telegram` ปัจจุบัน (เทียบ) |
|---|---|---|---|
| ขนาดที่ส่ง (ปก 4:3) | 2048×1536 | 960×720 | 1280×960 |
| ความจุดิบ | 291 ไบต์ | 51 ไบต์ | 342 ไบต์ |
| PSNR ของการฝัง / ของไฟล์ที่ส่ง | 40.8 / 37.5 dB | 40.8 / 37.7 dB | 46.2 / 39.8 dB |
| JPEG คุณภาพ 30–80 | ✅ (≈0%) | ✅ (≈0%) | ✅ ถึง 35, ⚠️ ที่ 30 |
| WebP คุณภาพ 75–80 | ✅ (4–12%) | ✅ (2–8%) | ⚠️ เสียหาย |
| WebP คุณภาพ 50–60 | ✅ เฉียดฉิว (21–29%) | ✅ (15–19%) | ❌ |
| ถูกย่อ 0.6–0.9× (+ JPEG 75) | ✅ | ✅ | ✅ 0.75–0.95× |
| ถูกย่อ 0.47× (2048 → 960) | ❌ | ไม่เกี่ยว | ❌ |

ตัวเลขนี้ยังไม่รวมการครอป และยังไม่ได้ลองกับตาราง quantization แปลก ๆ หรือ encoder ที่ปรับค่าแบบ trellis (เช่น mozjpeg) ซึ่ง Facebook อาจใช้ ถ้าทำจริงควรเผื่อความจุไว้ราวครึ่งหนึ่งของตาราง คือ **ราว 100–150 ไบต์ที่ 2048 px และ 20–30 ไบต์ที่ 960 px** พอสำหรับข้อความสั้นหรือรหัสนัดหมาย แต่ไม่พอสำหรับข้อความยาว

## ความเสี่ยง

- **เปลี่ยนได้ทุกเมื่อ** Meta ปรับขนาด รูปแบบไฟล์ หรือ encoder ได้โดยไม่ประกาศ profile ที่ใช้ได้วันนี้อาจพังพรุ่งนี้ และรูปที่ส่งไปแล้วจะถอดไม่ได้อีก
- **ผลไม่เหมือนกันในแต่ละที่** iOS, Android, เว็บ, แชตส่วนตัวกับแชตกลุ่ม, Wi-Fi กับเน็ตมือถือ อาจได้ผลต่างกัน ผู้ใช้จะเจอแบบ "บางครั้งได้ บางครั้งไม่ได้" ซึ่งน่าหงุดหงิดกว่าไม่ได้เลย
- **รูปดูแย่ลง** step 64 ทำให้ท้องฟ้าหรือผนังเรียบมีลายจาง ๆ ที่สังเกตได้ถ้าตั้งใจดู
- **ถูกจับได้ง่ายกว่า** QIM ที่แรงขึ้นทิ้งร่องรอยทางสถิติชัดขึ้น ข้อความยังเป็นความลับ (เข้ารหัสอยู่) แต่ซ่อน "การมีอยู่" ได้แย่ลง
- **ผู้รับบันทึกผิดไฟล์** ถ้าผู้รับแคปหน้าจอ หรือบันทึกจาก preview ใน feed ข้อมูลหายแน่นอน ต้องสอนผู้ใช้
- **ค่าใช้จ่ายในการดูแล** ต้องกลับมาทดสอบใหม่เป็นระยะ ซึ่งทำอัตโนมัติไม่ได้ (ดูเรื่องเงื่อนไขการใช้งาน)

## แผนทดสอบด้วยมือ

ใช้บัญชีจริงของเจ้าของโปรเจกต์ และบัญชีของเพื่อนที่ยินยอมร่วมทดสอบ (หรือบัญชีที่สองของตัวเองถ้ามี) ส่งในแชตส่วนตัว และโพสต์ที่ตั้งผู้ชมเป็น "เฉพาะฉัน"

### Phase A: ดูว่ารูปถูกทำอะไร (ไม่ต้องมีโค้ดใหม่)

เตรียมรูปทดสอบ (ใช้รูปถ่ายธรรมดาที่ไม่มีอะไรส่วนตัว):

| ชื่อ | ไฟล์ | เพื่อดูว่า |
|---|---|---|
| A1 | JPEG 4000×3000 คุณภาพ 95 | ถูกย่อเหลือเท่าไร |
| A2 | JPEG 2048×1536 คุณภาพ 95 | ขนาดพอดี tier ถูกย่อหรือบีบซ้ำไหม |
| A3 | PNG 2048×1536 | PNG ถูกแปลงเป็นอะไร |
| A4 | JPEG 960×720 คุณภาพ 95 | tier เล็ก |
| A5 | JPEG 2047×1535 คุณภาพ 95 | ขนาดไม่ลงตัวถูกปัดไหม |
| A6 | ไฟล์ที่ได้จาก profile `telegram` และ `line` ปัจจุบัน | profile ที่มีอยู่รอดไหม (ใช้ต่อใน Phase B) |

ส่งแต่ละรูปผ่าน:

1. Messenger แชตส่วนตัว ปิด HD
2. Messenger แชตส่วนตัว เปิด HD
3. Messenger แชตกลุ่ม (สร้างกลุ่มเล็กกับเพื่อนที่ร่วมทดสอบ)
4. โพสต์ Facebook ผู้ชม "เฉพาะฉัน" (รูปเดียว และอัลบั้มหลายรูป)

ทำซ้ำจากแอป iOS, แอป Android และเว็บ เท่าที่มี และลองทั้ง Wi-Fi และเน็ตมือถือสำหรับ Messenger

ฝั่งผู้รับให้ **บันทึกรูปด้วยเมนู "บันทึกรูป/ดาวน์โหลด" เท่านั้น ห้ามแคปหน้าจอ** บนเว็บให้เปิดรูปเต็มในแท็บใหม่ก่อนแล้วค่อยบันทึก และจด URL ไว้ด้วย (ดูค่า `stp=`) แล้วจดผลลงตาราง:

| รูป | ช่องทาง | อุปกรณ์ส่ง → รับ | เน็ต | รูปแบบไฟล์ | ขนาด (px) | ขนาดไฟล์ | chroma | คุณภาพโดยประมาณ | EXIF |
|---|---|---|---|---|---|---|---|---|---|
| A1 | Messenger ปิด HD | iOS → Android | Wi-Fi | | | | | | |

ข้อมูลในตารางหาได้จากคำสั่งที่มีอยู่แล้ว เช่น `identify -verbose ไฟล์.jpg` ของ ImageMagick (ดูบรรทัด `Quality`, `sampling-factor` และ `Geometry`) หรือ `exiftool ไฟล์` ถ้าไฟล์ขึ้นต้นด้วย `RIFF....WEBP` แปลว่าเป็น WebP

### Phase B: ลองของจริงกับ profile ที่มีอยู่

เมื่อ CLI รองรับ robust mode แล้ว ให้ถอดรูป A6 ทุกไฟล์ที่ได้กลับมา แล้วจดว่า `Found`, `Damaged` หรือ `NotFound` พร้อมค่า raw bit error rate ที่ตัวถอดรายงาน ถ้า profile `telegram` รอดใน Messenger แบบปกติอยู่แล้ว อาจไม่ต้องทำ profile ใหม่สำหรับ Messenger เลย

### Phase C: ทดสอบ prototype

ถ้า Phase A/B ชี้ว่าต้องทำ ให้สร้าง `facebook-2048` / `facebook-960` ตามค่าข้างบน แล้วทำซ้ำ Phase B อย่างน้อย 3 วันที่ต่างกัน เพราะผลอาจเปลี่ยนตามช่วงเวลาและภาระของเซิร์ฟเวอร์ ถ้ารอดน้อยกว่า 9 ใน 10 ครั้งในช่องทางใด ให้ถือว่าช่องทางนั้นใช้ไม่ได้

## เรื่องเงื่อนไขการใช้งาน

เงื่อนไขของ Meta ไม่ได้พูดถึงการซ่อนข้อมูลในรูปโดยตรง แต่มีข้อที่เกี่ยวข้องกับการทดสอบแบบนี้ เช่น ต้องใช้บัญชีจริงของตัวเองและห้ามสร้างบัญชีปลอม, ห้ามเข้าถึงหรือดึงข้อมูลจากบริการด้วยวิธีอัตโนมัติโดยไม่ได้รับอนุญาต, และห้ามใช้บริการทำสิ่งที่ผิดกฎหมาย หลอกลวง หรืออัปโหลดโค้ดอันตราย เนื้อหาในรูปก็ยังต้องเป็นไปตาม Community Standards แผนทดสอบข้างบนจึงทำด้วยมือทั้งหมด ใช้บัญชีจริงกับเพื่อนที่ยินยอม และตั้งค่าให้เป็นส่วนตัว ก่อนเริ่มควรอ่านเงื่อนไขฉบับล่าสุดอีกครั้ง เพราะเปลี่ยนได้
